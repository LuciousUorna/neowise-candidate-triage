# Тестовое Neowise. AI-помощник для входящих заявок

Ориентир — 45–60 минут. Менеджер вводит текст заявки, получает тему и черновик ответа. Он читает результат и сам решает, что отправить клиенту.

## Запуск

В репозитории есть сервер, HTML-страница и имитатор модели. Нужен Node.js 20 или новее. Зависимостей и ключей нет.

```sh
npm start
# или без npm:
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт можно задать через переменную `PORT`, лимит ожидания модели — через `MODEL_TIMEOUT_MS` (по умолчанию 300 мс).

## Тесты

```sh
npm test
# или без npm:
node --test
```

Тесты полностью офлайн и детерминированные, прогон занимает меньше секунды: сервер поднимается на свободном порту, имитатор модели используется настоящий, а медленные сценарии проверяются с коротким дедлайном вместо реального ожидания.

## Что изменить

1. Доработайте `POST /api/triage`. Принимайте JSON с полем `text`, содержащим непустую строку. При пустом, отсутствующем, нестроковом вводе или битом JSON верните HTTP 400 и `{"status":"invalid_input"}`.
2. При корректном ответе модели верните HTTP 200 и `{"status":"ready","topic":"…","draft":"…"}`. Допустимые темы — `delivery`, `pricing`, `other`. Черновик должен быть непустой строкой. При таймауте, ошибке модели или неподходящем ответе верните HTTP 200 и `{"status":"manual_review","topic":null,"draft":null}`. Ограничьте ожидание модели 300 мс. Оставьте поведение выданного имитатора прежним.
3. Покажите на странице тему и черновик при успехе. Для `manual_review` покажите понятное сообщение менеджеру и очистите предыдущий черновик. Добавьте хотя бы один исполнимый тест для поведения при сбое и инструкцию его запуска.

Для локальной проверки имитатор принимает любой обычный текст. Метки `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` включают отдельные сценарии сбоя.

## Что изменено

- `server.mjs` — три явные границы проверки: тело запроса, поле `text`, ответ модели. Ввод проверяется до вызова модели, поэтому на пустой заявке модель не вызывается вообще. Вызов модели ограничен дедлайном (`AbortSignal.timeout` + гонка), так что страница получает ответ даже если модель проигнорирует отмену. Ответ модели разбирается и валидируется строго: только темы `delivery`/`pricing`/`other` и непустой черновик попадают к менеджеру, всё остальное — `manual_review` с кодом причины. Сервер экспортирует `createTriageServer()` с подстановкой модели и дедлайна, за это зацеплены тесты.
- `triage-ui.mjs` — новый модуль с чистой логикой отображения: ответ API → что показать менеджеру. Черновик непустой ровно в одном случае (`ready`), поэтому «залипший» черновик невозможен по построению. Модуль без DOM и сети, проверяется обычным `node --test`.
- `index.html` — вместо дампа JSON читаемые состояния: готовый черновик, «Нужен ручной разбор» с причиной, отклонённый ввод, недоступный сервис. Перед каждым запросом черновик очищается, кнопка блокируется на время запроса, есть клиентский таймаут на случай неответа сервиса.
- `triage.test.mjs`, `package.json` — 23 теста на `node:test`, команды `npm start` и `npm test`. Зависимостей не добавлялось.
- `mock-ai.mjs` не изменялся.

## Поведение при сбоях

| Случай | HTTP | Ответ | Что видит менеджер |
|---|---|---|---|
| Корректная заявка | 200 | `status: ready`, `topic`, `draft` | тема и черновик ответа |
| Пустой текст или только пробелы | 400 | `status: invalid_input`, `reason: text_empty` | «Заявка не принята» + причина |
| Поля `text` нет или это не строка | 400 | `status: invalid_input`, `reason: text_not_string` | «Заявка не принята» + причина |
| Битый JSON в теле запроса | 400 | `status: invalid_input`, `reason: invalid_json` | «Заявка не принята» + причина |
| Модель не ответила за 300 мс (`[timeout]`) | 200 | `status: manual_review`, `reason: model_timeout` | «Нужен ручной разбор», черновик очищен |
| Ошибка модели (`[error]`) | 200 | `status: manual_review`, `reason: model_error` | «Нужен ручной разбор», черновик очищен |
| Ответ модели не JSON (`[bad-json]`) | 200 | `status: manual_review`, `reason: model_output_not_json` | «Нужен ручной разбор», черновик очищен |
| Недопустимая тема (`[bad-topic]`) | 200 | `status: manual_review`, `reason: model_topic_unknown` | «Нужен ручной разбор», черновик очищен |
| Пустой черновик (`[empty-draft]`) | 200 | `status: manual_review`, `reason: model_draft_empty` | «Нужен ручной разбор», черновик очищен |
| Ответ модели не того формата | 200 | `status: manual_review`, `reason: model_output_shape` | «Нужен ручной разбор», черновик очищен |
| Неизвестный маршрут или метод | 404 | `status: not_found` | — |
| Непредвиденная ошибка сервера | 500 | `status: server_error` | «Нужен ручной разбор», черновик очищен |
| Сервис недоступен или молчит дольше 5 с | — | ответа нет | «Нужен ручной разбор», черновик очищен |

При `invalid_input` и `manual_review` поля `topic` и `draft` всегда `null`: непроверенный текст модели физически не доходит до страницы. Каждый отказ сопровождается машинным кодом `reason` и человеческим пояснением `message`.

## Польза для менеджера

- Клиенту не уйдёт мусорный черновик: текст модели показывается только после проверки темы и непустоты, остальное помечается как ручной разбор.
- Старый черновик не остаётся на экране рядом с новой заявкой — очистка происходит до запроса, поэтому перепутать ответы двух клиентов нельзя.
- Любой сбой заканчивается понятной инструкцией «нужен ручной разбор» с причиной, а не техническим дампом и не тишиной — заявка не теряется, а переходит к человеку.
- Время ответа предсказуемо: ожидание модели ограничено 300 мс, страница — 5 с, так что менеджер не ждёт зависший запрос.
- Поведение при сбоях закрыто тестами (`npm test`), поэтому доработки не вернут старые проблемы незаметно.

Измеримо: доля заявок со статусом `manual_review` и доля отправленных клиентам ответов, которые пришлось переписывать после отправки — первая показывает, сколько работы честно ушло человеку, вторая должна стремиться к нулю.
