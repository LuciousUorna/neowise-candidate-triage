# Тестовое Neowise. AI-помощник для входящих заявок

Ориентир — 45–60 минут. Менеджер вводит текст заявки, получает тему и черновик ответа. Он читает результат и сам решает, что отправить клиенту.

## Запуск

В репозитории есть сервер, HTML-страница и имитатор модели. Нужен Node.js 20 или новее. Зависимостей и ключей нет.

```sh
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт можно задать через переменную `PORT`.

## Что изменить

1. Доработайте `POST /api/triage`. Принимайте JSON с полем `text`, содержащим непустую строку. При пустом, отсутствующем, нестроковом вводе или битом JSON верните HTTP 400 и `{"status":"invalid_input"}`.
2. При корректном ответе модели верните HTTP 200 и `{"status":"ready","topic":"…","draft":"…"}`. Допустимые темы — `delivery`, `pricing`, `other`. Черновик должен быть непустой строкой. При таймауте, ошибке модели или неподходящем ответе верните HTTP 200 и `{"status":"manual_review","topic":null,"draft":null}`. Ограничьте ожидание модели 300 мс. Оставьте поведение выданного имитатора прежним.
3. Покажите на странице тему и черновик при успехе. Для `manual_review` покажите понятное сообщение менеджеру и очистите предыдущий черновик. Добавьте хотя бы один исполнимый тест для поведения при сбое и инструкцию его запуска.

Для локальной проверки имитатор принимает любой обычный текст. Метки `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` включают отдельные сценарии сбоя.

## Решение: как запустить и проверить

```sh
npm start
# или без npm:
node server.mjs
```

```sh
npm test
# или без npm:
node --test
```

Тесты офлайн и детерминированные, прогон занимает меньше секунды: сервер поднимается на свободном порту, имитатор модели используется настоящий, а медленные сценарии проверяются с коротким дедлайном вместо реального ожидания. Порт задаётся через `PORT`, лимит ожидания модели — через `MODEL_TIMEOUT_MS` (по умолчанию 300 мс). Значение проверяется один раз при старте: если это не целое число от 1 мс, сервер печатает причину и не поднимается.

## Решение: что изменено

- `server.mjs` — три явные границы проверки: тело запроса, поле `text`, ответ модели. Ввод проверяется до вызова модели, поэтому на пустой заявке модель не вызывается. Вызов модели ограничен дедлайном: модели отправляется `signal`, но ответ не ждём, таймер снимается на любом исходе. Исключение модели, в том числе синхронное, остаётся обычным сбоем и даёт `manual_review`. Ответ модели разбирается строго: к менеджеру попадают только темы `delivery`/`pricing`/`other` с непустым черновиком.
- `triage-ui.mjs` — новый модуль с чистой логикой отображения: статус ответа API превращается в то, что видит менеджер. Черновик непустой ровно в одном случае (`ready`). Без DOM и сети, проверяется обычным `node --test`.
- `index.html` — вместо дампа JSON читаемые состояния: готовый черновик, «Нужен ручной разбор», отклонённый ввод, недоступный сервис. Перед каждым запросом черновик очищается, кнопка блокируется на время запроса, есть клиентский таймаут 5 с.
- `triage.test.mjs`, `package.json` — 33 теста на `node:test`, команды `npm start` и `npm test`. Зависимостей не добавлялось.
- `mock-ai.mjs` не изменялся.

## Решение: поведение при сбоях

| Случай | HTTP | Тело ответа | Что видит менеджер |
|---|---|---|---|
| Корректный ответ модели | 200 | `{"status":"ready","topic":"…","draft":"…"}` | тема и черновик ответа |
| Пустой текст, только пробелы, нет поля `text`, не строка, битый JSON | 400 | `{"status":"invalid_input"}` | «Заявка не принята» и просьба проверить текст |
| Таймаут 300 мс (`[timeout]`), ошибка модели (`[error]`), ответ не JSON (`[bad-json]`), неизвестная тема (`[bad-topic]`), пустой черновик (`[empty-draft]`), иной формат ответа | 200 | `{"status":"manual_review","topic":null,"draft":null}` | «Нужен ручной разбор», черновик очищен |
| Неизвестный маршрут или метод | 404 | `{"status":"not_found"}` | — |
| Непредвиденная ошибка сервера | 500 | `{"status":"server_error"}` | «Нужен ручной разбор», черновик очищен |
| Сервис не ответил за 5 с | — | ответа нет | «Нужен ручной разбор», черновик очищен |

Тела ответов ровно такие, как в задании: причина отказа в них не возвращается. Вместо этого сервер пишет одну строку в лог на каждый отказ:

```
triage_failure status=manual_review reason=model_timeout elapsed_ms=301
```

Коды причин: `invalid_json`, `text_not_string`, `text_empty`, `model_timeout`, `model_error`, `model_output_not_json`, `model_output_shape`, `model_topic_unknown`, `model_draft_empty`, `unhandled_exception`. Текст заявки в лог не попадает. Текст для менеджера формируется на странице по статусу ответа.

## Решение: польза для менеджера

Непроверенный ответ модели не доходит до менеджера, а любой сбой заканчивается понятным «нужен ручной разбор» вместо пустого экрана или чужого черновика; измерить можно по числу заявок с `manual_review` за период и разбивке по `reason` из лога.

## Решение: известные ограничения

- Размер тела запроса не ограничен.
- `trim()` не убирает невидимые символы вроде zero-width space, поэтому такой текст считается непустым и уходит в модель.
- Скрипт страницы (`index.html`) проверен вручную в браузере; тестами покрыты чистые функции отображения из `triage-ui.mjs`, но не привязка к DOM.
